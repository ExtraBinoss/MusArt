# Project thumbnail lifecycle

Project lists contain small manifests and composition summaries. Original assets, history events and thumbnail blobs have separate IndexedDB stores. A visible card loads thumbnail blobs for its active composition and its neighbour through `loadProjectThumbnails(projectId, pageIds)`. It receives a lease containing object URLs; releasing that lease allows eviction. Active URLs are never revoked by the inactive LRU budget (80 entries / 32 MiB). A project/page revision change invalidates the previous URL after its last user releases it.

Thumbnails are native WebP blobs, with quality 0.88 and a maximum edge of 768 pixels. The GPU render session is retained across compositions and uses a 96 MiB hard resource budget. Its original image inputs are resized once with the browser's `createImageBitmap` API, to a maximum source edge of 640 pixels. No Canvas2D composition, JavaScript pixel array or GPU readback is used. Native image bitmaps are closed when their GPU cache entry is disposed. Regular editor preview and full-resolution export retain their original source resolution.

Pixel revisions use SHA-256 over canonical composition paint metadata and cached original digests. Renaming, guides, locks and layout annotations do not invalidate the thumbnail. Original digest retention is bounded to 128 entries / 64 MiB of referenced source strings. Render results are persisted only if the manifest still contains the same project, composition and pixel revision; deletion or a later edit cannot be overwritten by an old asynchronous render.

The scheduler observes committed engine project snapshots. React color/geometry previews do not enter its queue. It coalesces changes for 600 ms, requests an idle slot with at least 8 ms remaining, and postpones work during pointer approach, gestures, keyboard input and trackpad activity. An exhausted idle-timeout callback reschedules rather than forcing GPU work. Supported browsers also report queued native input through `isInputPending`. Activity is checked again after asynchronous source preparation and before GPU submissions. There is no idle render loop. At most eight pending project snapshots are retained.

Transient layer/effect and export previews borrow exactly the same retained renderer through `ThumbnailPipeline.preview(key, page, assets, options)`. Their queue deduplicates consumers, bounds pending jobs to 32 and retains at most 64 blob results within 8 MiB. Keys must encode every paint variant and revision; edges distinguish 96-pixel layer previews from 384-pixel export previews. Abort signals and current-origin guards are checked before preparation, before GPU work and before delivery. Consumers own any temporary object URLs they create from returned blobs.

Background previews yield to canonical thumbnails and the 600 ms input quiet period. Explicit export popovers request `priority: "foreground"`; after pointer release they bypass that artificial quiet period and run before queued canonical/background jobs, without interrupting an active render. Held pointers and live wheel bursts still defer all optional GPU work. Disposal rejects pending consumers, drains active work and then closes the single shared render session.

Before native WebP encoding, the retained frame yields one browser task and checks activity/disposal again. This lets queued input cancel an optional encode before `toBlob` can synchronously flush the canvas. The yield uses native task scheduling when available and one abortable timer otherwise; it does not add another renderer or worker. Once a native encoding call begins, it cannot be preempted; a late result after disposal is rejected. These guards protect scheduling boundaries and do not claim to eliminate unrelated React/layout work during selection.

Ordinary project save/load does not await GPU generation. The explicit `flushThumbnails()` service and automation port first persist canonical changes, then wait until queued thumbnails finish when input is quiet. Tests and headless clients can use it before taking a performance baseline. Runtime disposal cancels pending work, waits for active work and releases its retained session and object URLs.

New project, duplicate-project, colliding portable-import and original mask-asset identifiers use `crypto.randomUUID()`. Their persistence identities remain unique across browser sessions. The pure engine's local identifiers remain suitable for document layers and guides.

The unit suite covers coalescing, selected-page loading, stale result rejection, deletion, activity suspension, resource cleanup, URL leases, revision invalidation, native encoding failures, UUID persistence and StrictMode aborts before the first storage write. Native browser checks confirm resized image orientation on both Three backends and successful WebP decoding. Project-card browser scenarios validate persisted composition previews and the library's CRUD and carousel interactions.
