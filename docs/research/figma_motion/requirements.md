# Motion and video requirements

This inventory translates the user's Motion discussion into testable obligations. The authoritative French wording, including tentative ideas and corrections, is preserved in [the verbatim brief](user-brief.fr.md). Assistant suggestions do not become user requirements through repetition.

## Classification and traceability

| Mark  | Meaning                                                                                                                                |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **H** | Explicit user requirement or design instruction; preserve it in the delivery checklist.                                                |
| **P** | Explicit experience target or future direction; preserve it, define its scope and report evidence honestly.                            |
| **D** | Derived acceptance rule needed to make an explicit requirement coherent; identify the proposal rather than attributing it to the user. |
| **G** | Existing repository guardrail; it constrains implementation independently of this feature request.                                     |

[M1](user-brief.fr.md#m1) introduces video/camera and time-driven properties; [M2](user-brief.fr.md#m2) prioritizes video effects, deterministic export and the separate Timelapse role; [M3](user-brief.fr.md#m3) and [M5](user-brief.fr.md#m5) explain the layer/compositing and workflow concerns. [M4](user-brief.fr.md#m4) rejects premature coding during exploration. [M6](user-brief.fr.md#m6) subsequently authorizes an isolated implementation with detailed requirements and supplied screenshots. [M7](user-brief.fr.md#m7) adds the documentation, research and delegated-checklist preparation now in progress. [M8](user-brief.fr.md#m8) fixes Mediabunny as the exporter and asks for questions where decisions remain. [M9](user-brief.fr.md#m9) explicitly requires instant-feeling scrubbing backward and forward. The user answers in [M10](user-brief.fr.md#m10), [M11](user-brief.fr.md#m11) and [M12](user-brief.fr.md#m12) settle Static base-design behavior, automatic local proxies and source-video audio controls respectively. [M13](user-brief.fr.md#m13), [M14](user-brief.fr.md#m14) and [M15](user-brief.fr.md#m15) confirm active-artboard-only playback, extending duration for longer imported video without shortening existing tracks, and counting every layer receiving a track, including groups and descendants. [M16](user-brief.fr.md#m16) schedules camera/live input for the next step after video and timeline stabilization. [M17](user-brief.fr.md#m17) chooses an Export split button with a small downward chevron and a Timelapse export option. [M18](user-brief.fr.md#m18) narrows Timelapse to a simplified dialog that fits the complete creation replay into a requested final duration of 1–30 seconds. [M19](user-brief.fr.md#m19) explicitly requires a generic, headless-capable animation engine and readable, maintainable, smooth implementation.

Every build task must reference these stable IDs and record its actual verification. A checkbox, authored test or mockup is not proof that the behavior has passed.

## Keyframes, effects and property editing

| ID     | Class | Requirement                                                                                        | Acceptance criteria                                                                                                                                                                                                                                                   | Source                  |
| ------ | ----- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| KEY-01 | H     | Add keyframes from properties through a small diamond control, in the reference's style.           | Supported inspector fields expose a visible, accessible diamond and show whether the property is unanimated, animated or keyed at the current time. The first click establishes a real keyframe at the playhead.                                                      | M6 and both screenshots |
| KEY-02 | H     | After the first keyframe, editing the property at another time creates the next keyframe directly. | Arm a property with its diamond, move the playhead and edit its value: a new keyframe appears for that property at that time. | KEY-04 | H     | All existing effects must be applicable to video and support animation of suitable parameters.     | Every type in the actual effect catalog is covered by a capability inventory and tests; the implementation must not silently cover only a handpicked subset. Numeric, color and discrete settings have explicit temporal semantics and retain valid authored values.  | M1, M2, M6              |
| KEY-05 | P     | Support motion of suitable layer properties and colors, beyond a few effect controls.              | Inventory transforms, opacity, paint and other supported properties. An effect being applied to every video frame is separate from animating its parameters or its internal phase. Preserve that distinction from M3: adding an effect must not force all of its controls to change over time.

## Existing engineering guardrails

| ID   | Class | Guardrail and consequence                                                                                                                                                                                                                                            |
| ---- | ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G-01 | G     | Pure temporal documents, validation, commands and evaluation belong in `packages/core`; no DOM, storage, React or GPU objects enter portable data.                                                                                                                   |
| G-02 | G     | Rendering continues through Three.js WebGPURenderer/R3F/TSL and its WebGL fallback. Composition/effects/masks remain GPU textures without production GPU pixel readbacks into JavaScript.                                                                            |
| G-03 | G     | Document edits use validated commands and atomic transactions. A completed gesture creates one undo entry; cancellation restores its original state. Playback and scrubbing are presentation work, with stale origin checks.                                         |
| G-04 | G     | Media/storage/GPU work is bounded, lazy and explicitly owned. Related writes are atomic; async results cannot overwrite a newer project or resurrect deleted content. Dispose textures, decoders, frames, workers, tracks, timers and URLs.                          |
| G-05 | G     | Preserve English/French UI resources, English technical documentation, asset provenance, mirrored tests, file-size rules, focused verification, measured browser evidence, zero rule violations before commits, synchronized versions and English changelog entries. |

These guardrails come from [AGENTS.md](../../../AGENTS.md) and [architecture contracts](../../architecture/contracts.md). TIM-02 records the explicit user override for the recenter affordance; it must not be used to discard unrelated navigation rules such as pointer-centered zoom or fit/reset access.
