# Motion performance investigation

This is an unfinished investigation on `feat/motion-video`, not a performance sign-off. The acceptance workloads are the actual **In Bloom** and **Motion Stress Lab** templates opened through the application. Small fixtures establish individual contracts but cannot replace these workloads. M44 requests one dedicated performance agent; the parent coordinates verification and the other agents remain idle.

## Acceptance boundaries

| Boundary       | Required evidence                                                                                                                                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Timeline input | Native hover, clicks, tooltips, opening/closing, scrolling, zoom and scrub. Record input dispatch, next RAF, subsequent presentation opportunity, Event Timing and long tasks separately.                                                               |
| React          | Record actual commits of App, Inspector, CanvasArea, EditorCanvas, EditorScene and the timeline. A zero commit count alone does not establish low latency.                                                                                              |
| Frame budget   | Target approximately 16.67 ms at 60 Hz. Intentional 130/180 ms panel transitions and tooltip delays are separate from per-frame CPU cost and input latency.                                                                                             |
| Video          | Record requested composition time, source PTS and the time actually submitted for presentation. A responsive playhead does not establish a responsive decoded image. Separate cold seek, warm forward playback, reverse, loop boundaries and ping-pong. |
| GPU            | Three.js owns compositing/effects and VideoFrameTexture. Instrument actual production read APIs; no GPU pixel readback into JavaScript. Native source/texture leases survive until real GPU acknowledgments and are disposed explicitly.                |
| Browser        | Chrome/Chromium headless is the current requested reference. Record actual adapter, GPU compositing/rasterization/decoder status, version, viewport, CPU limits and memory pressure. Firefox requires later independent verification.                   |

## Measurement caveats

- Detailed invalidation tracing substantially changes timings. One production close grew from roughly 90 ms without tracing to over one second with tracing. Such traces establish attribution, not user latency.
- Keep three distinct runs: clean latency with no profiler enabled; CPU-only sampling with matching source maps; detailed layout/invalidation capture only when needed.
- Preserve dirty-source hashes, compiled bundles/maps, environment, raw samples and failures under ignored `artifacts/`. Do not overwrite a failing cohort with the next run.
- Initial production cohorts used a 200% CPU scope. Throttling occurred during playback; a 400% comparison removed that throttling without removing the video delay. Never combine their distributions.
- Swap was full on the shared workstation, but observed renderer major-fault deltas and PSI did not explain the recurrent warm stalls. Continue recording pressure and stop heavy work when memory pressure appears; do not terminate user applications.
- Two obsolete automation Chromium process trees were subsequently found running, including a GPU process consuming over six CPU cores. Both owned test-browser trees were stopped; available memory increased from approximately 2.5 GB to 9.7 GB. Earlier absolute latency cohorts include this contention and must not be presented as an isolated hardware envelope. Functional pixel and cleanup checks remain separately recorded. Follow-up checks are serialized, low priority, capped at one logical CPU and kept brief; no new broad profiling or stress batch is authorized by the current resource constraint.
- Actual Chrome GPU information confirms Intel/Vulkan hardware compositing, rasterization, WebGPU and video decoding. Adapter presence alone would not establish hardware DOM compositing.
